# Rust workspace and core logic: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Cargo workspace in `windows-linux/` whose `snapline-core` crate does everything
`macOS/Sources/SnaplineCore/` does except `SymbolRepair`, tested on Windows and Linux in GitHub Actions.

**Architecture:** One library crate with no UI and no OS calls, one module per Swift file. The Swift code is the
reference implementation. Behaviour is pinned by the Swift tests, ported one for one, plus shared JSON test cases
that both the Swift and the Rust tests read.

**Tech Stack:** Rust (edition 2024, stable), `regex`, `fancy-regex`, `sha2`, `hmac`, `base64`, `rand`, `chrono`,
`serde`, `serde_json`, `url`. GitHub Actions on `windows-latest` and `ubuntu-latest`.

**Spec:** [docs/windows-linux.md](../windows-linux.md)

## Global Constraints

- Work on branch `feat/windows-linux-rust`. Every commit GPG-signed (check with `git log --format='%h %G?'`, expect
  `G`). No AI attribution lines in commit messages.
- TDD: write the Rust test first, run it, and see it fail before writing the code.
- `snapline-core` must not depend on any UI, OS-specific or network crate.
- Add crates with `cargo add <name>` (latest stable). Do not pin by hand.
- Fake secrets in tests and fixtures must be split so GitHub secret scanning does not flag them (see Task 2).
- `cargo fmt --check` and `cargo clippy --all-targets -- -D warnings` must pass.
- Do not change the Swift code's behaviour. The only Swift change allowed is reading shared fixtures in tests.

## Why the implementation steps translate instead of quoting code

Each module is a direct translation of one Swift file, 18 to 160 lines long. Copying that code into this plan would
create a third copy to keep in sync. The steps name the Swift file to translate and list every place where Rust
needs a different approach. The tests, which define the behaviour, are written out in full or ported one for one
from a named Swift test file.

## Review Focus

1. **Dates, versions and prices read as phone numbers.** `NSDataDetector` ignores `2026-10-28`, `1.250.000` and
   `#48213`; a hand-written phone pattern easily flags them. Covered by fixture cases in Task 2 and Task 3.
2. **Byte and character ranges.** Swift ranges count UTF-16 units, Rust slices count bytes. Text with `é`, `⌘` or
   emoji before a match must hide exactly the match. Covered in Task 3, step 1.
3. **Card numbers and IBANs next to other digits.** `(?<!\d)` and `(?!\d)` must stay; `regex` silently cannot express
   them. Covered by fixture cases.
4. **SigV4 with special characters in the key.** Spaces, `+` and non-ASCII in object keys must be encoded exactly as
   AWS expects. Covered by the ported `SigV4Tests` cases in Task 4.
5. **OAuth callback with a wrong or missing `state`.** Must be an error, never a code. Covered by the ported
   `GoogleOAuthTests` in Task 5.

- [ ] **Step 3: Implement**

Translate `macOS/Sources/SnaplineCore/SensitiveText.swift`. Differences from Swift:

- Rules whose pattern has `(?<!`, `(?<=`, `(?!` or `(?=` use `fancy_regex::Regex`; the others use `regex::Regex`.
  Wrap both in a small `enum Pattern { Plain(regex::Regex), Fancy(fancy_regex::Regex) }` with one
  `captures_iter`-style method returning `(Range<usize>, Option<Range<usize>>)` for the whole match and the group.
  Build all rules once in a `std::sync::LazyLock<Vec<Rule>>`.
- `NSRange` and `NSString` become byte ranges on `&str`. `extendToWordEnd` walks `char_indices()` forward until
  whitespace.
- `NSDataDetector` phone numbers become one `fancy_regex` pattern for phone-shaped runs: an optional `+` or `(`,
  digits in groups of 2 to 5 separated by single spaces, `-`, `.` or `)`, with no digit, `.` or `-` directly before
  or after. Keep the Swift rule of 7 to 15 digits, and reject a run that is all one group of digits (that is an order
  number). Tune the pattern against the fixture cases, not by guessing: every case from Task 2 must pass.
- The `face` category has no text rule; it is handled by image analysis in Phase 4.
- `merge` sorts by start, then joins overlapping ranges, keeping the first match's category, as in Swift.

Add dependencies: `cargo add regex fancy-regex`.
